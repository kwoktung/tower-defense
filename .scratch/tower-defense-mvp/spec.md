# Spec: 塔防 MVP 骨架

Status: done

## Problem Statement

我想用 Phaser 4 和 TypeScript 做一个塔防游戏，但现在仓库是空的。如果直接按 Phaser 的常规写法，把逻辑写进 Scene 和 GameObject，会遇到这些问题：

- 游戏规则只能在浏览器里跑起来才能验证，没法快速写自动化测试。
- AI agent 改了代码之后，没有稳定的方法"看到"改动后的画面，也没法把画面和代码、数据对应起来，只能靠猜。
- 以后要把多边形换成正式美术时，渲染代码和逻辑缠在一起，换肤很痛苦。
- 以后关卡配置和玩家进度要存到 server 时，没有统一的数据接口，调用方要大面积改动。
- 没有一个像前端 Storybook 那样的地方，可以单独查看、调整每个游戏元素。

我需要的是一个**骨架**：玩法尽量简单，但结构要方便以后扩充塔、敌人、关卡、皮肤和数据后端。

## Solution

搭一个最小但完整的塔防游戏：一张地图、一条固定路径、2 种塔、2 种敌人、3 波怪，有金币、生命和胜负判定。所有对象都用彩色多边形表示，敌人用红色系，塔用冷色系。

在这个最小玩法下面，搭好四样东西：

1. **独立的 Simulation**：完全不依赖 Phaser 的纯 TS 游戏逻辑，以固定步长运行，随机数带种子。不启动浏览器就能测试，同样的输入每次得到同样的结果。
2. **可替换的 Skin**：渲染层只负责"把 Simulation 的快照画出来"。画法由 Skin 决定，MVP 提供 Polygon 皮肤。
3. **统一的数据服务接口**：关卡、单位配置、玩家进度的读写都走异步接口。MVP 用本地实现（打包进来的 JSON 和 localStorage），以后可以换成 server 实现，调用方不用改。
4. **可视化工作流**：用 Storybook 单独展示每个实体、地图、HUD 和由 Fixture 构造的 Scenario。可以切皮肤、开关 Debug overlay，还有一条命令批量生成截图（Shots），让 agent 能直接查看画面并对照数据。

## User Stories

### 玩家

1. 作为玩家，我希望打开页面就直接进入游戏，不需要经过菜单，这样马上就能开始玩。
2. 作为玩家，我希望看到一张地图，上面有清楚的敌人行进路径，这样我知道敌人从哪里来、往哪里去。
3. 作为玩家，我希望看到哪些格子可以造塔（Slot），这样我知道塔能放在哪里。
4. 作为玩家，我希望鼠标悬停在 Slot 上时，它会高亮并显示当前选中的塔的射程，这样我放塔前就能判断覆盖范围。
5. 作为玩家，我希望在 HUD 上选择要造的塔，并看到每种塔的名称和造价，这样我能做出选择。
6. 作为玩家，我希望钱不够时造塔按钮会变灰，这样我不会做无效操作。
7. 作为玩家，我希望点击空的 Slot 就能造出选中的塔并扣钱，这样操作简单直接。
8. 作为玩家，我希望点击已经有塔的 Slot 时什么都不发生，这样不会误操作。
9. 作为玩家，我希望有一个"开始下一波"按钮，由我决定什么时候开波，这样我可以先布置好防线。
10. 作为玩家，我希望当前一波还没结束时，"开始下一波"按钮是灰的，这样我知道现在还不能开波。
11. 作为玩家，我希望 HUD 上一直显示金币、生命和"第 n / N 波"，这样我随时了解局势。
12. 作为玩家，我希望普通敌人和快速敌人在外形和颜色上都能一眼分清，而且都是红色系，和我的塔明显不同，这样敌我一目了然。
13. 作为玩家，我希望每个敌人头上有血条，这样我能看出攻击有没有效果。
14. 作为玩家，我希望塔会自动攻击射程内走得最远的敌人，这样防线的行为符合直觉。
15. 作为玩家，我希望能看到子弹飞向敌人，敌人被击中时会闪一下，这样战斗有反馈。
16. 作为玩家，我希望溅射塔命中时有爆炸圈，并且圈内的敌人都受到伤害，这样两种塔的差别看得见。
17. 作为玩家，我希望击杀敌人能获得金币，这样我能继续造塔。
18. 作为玩家，我希望敌人走到路径终点时扣我的生命，这样漏怪有代价。
19. 作为玩家，我希望生命归零时立刻判负，并显示失败浮层，这样我知道游戏结束了。
20. 作为玩家，我希望清完全部 3 波、生命还没归零时判胜，并显示胜利浮层，这样我有明确的目标。
21. 作为玩家，我希望结束浮层上有"重来"按钮，这样可以马上再玩一局。
22. 作为玩家，我希望游戏结束时自动保存我在这一关的最好成绩，这样刷新页面后记录还在。
23. 作为玩家，我希望游戏画面在不同大小的浏览器窗口里都能等比缩放、完整显示，这样不会被裁掉。

### 开发者

24. 作为开发者，我希望 Simulation 完全不依赖 Phaser，并且有 lint 规则强制这一点，这样逻辑始终可以在 Node 里测试。
25. 作为开发者，我希望 Simulation 以固定 60Hz 步长运行，和渲染帧率无关，这样游戏行为不受机器性能影响。
26. 作为开发者，我希望所有随机数都来自一个带种子的 RNG，这样同一个种子加同样的操作，每次结果都一样。
27. 作为开发者，我希望能用 `advance(ticks)` 精确推进 Simulation，并拿到这段时间内产生的全部 SimEvent，这样测试和 story 都能精确控制时间。
28. 作为开发者，我希望能从任意 SimState 创建 Simulation，这样可以直接构造想测试的局面，不用先把游戏跑到那一步。
29. 作为开发者，我希望 SimState 完全可序列化，这样可以打印、保存、对比状态。
30. 作为开发者，我希望玩家操作是 Simulation 上的方法，并且返回明确的成功或失败原因，这样 UI 能给出准确反馈，测试也能断言。
31. 作为开发者，我希望塔、敌人、波次、地图都由 JSON 配置驱动，并在加载时校验，这样新增内容不需要改逻辑代码。
32. 作为开发者，我希望 TS 类型由配置 schema 推导出来，而不是手写第二份，这样类型和校验永远一致。
33. 作为开发者，我希望配置里引用了不存在的单位 kind 时，加载就失败，并给出带路径的错误信息，这样配置错误能尽早发现。
34. 作为开发者，我希望新增一种塔（攻击方式仍是单体或溅射）只需要改三处：配置里加一项、Polygon 皮肤里加一个形状、加一个 story，这样骨架真的方便扩充。
35. 作为开发者，我希望有一个 Fixture builder，可以链式描述"什么关卡、多少钱、哪些塔、哪些敌人在路径的什么位置"，这样构造测试局面很省事。
36. 作为开发者，我希望单元测试和 story 用的是**同一份**具名 Fixture，这样测过的局面也一定能看得到。
37. 作为开发者，我希望在 Storybook 里能单独看每种塔、敌人、子弹的各种状态，这样调视觉时不用进游戏。
38. 作为开发者，我希望每个 story 都能用 Controls 切换皮肤、开关 Debug overlay，这样方便对比不同皮肤和查看调试信息。
39. 作为开发者，我希望 Scenario story 默认是静态画面，也能切换成运行状态、调整速度、先快进 N 个 tick 再显示，这样既有稳定画面，也能观察变化过程。
40. 作为开发者，我希望在 Storybook 里切换 story 或改参数时，旧的 Phaser 实例会被正确销毁，这样不会出现 WebGL context 泄漏。
41. 作为开发者，我希望在 Storybook 里有一个完整可玩的游戏 story，这样不用另外启动开发服务器也能试玩。
42. 作为开发者，我希望游戏里按 `D` 可以开关 Debug overlay，这样手动试玩时也能看到射程、id、血量。
43. 作为开发者，我希望能用 URL 参数选择皮肤，这样不用改代码就能看换肤效果。
44. 作为开发者，我希望每个 story 都自动做一次冒烟测试（能渲染、不报错），这样视觉层的大问题能自动发现。

### AI agent

45. 作为 agent，我希望一条命令就能把所有 story 截成 PNG，并写到固定目录，这样我能直接打开图片查看画面。
46. 作为 agent，我希望每个 story 都有开 Debug overlay 和不开两张截图，这样既能看最终效果，也能核对 id、坐标、射程等数据。
47. 作为 agent，我希望能按名称筛选，只截部分 story，这样改了一处就能快速验证。
48. 作为 agent，我希望能对同一个 Scenario 按多个 tick 数分别截图，这样能看到局面如何变化。
49. 作为 agent，我希望截图的文件名能直接对应到 story，story 对应到 Fixture，Fixture 对应到测试，这样我能从画面追溯到代码。
50. 作为 agent，我希望同一个 story 每次截图的结果都一样，这样我比较修改前后的截图时，看到的差异一定来自我的修改。
51. 作为 agent，我希望 Debug overlay 用一种固定的颜色（青色细线加等宽字体），和游戏内容明显不同，这样我不会把调试信息当成游戏元素。
52. 作为 agent，我希望项目的 agent 说明文件里写明开发命令和工作约定（改了渲染要跑 Shots 并查看截图；新加的视觉元素要配 story 和 Fixture），这样我知道该怎么验证自己的改动。
53. 作为 agent，我希望有一份术语表（CONTEXT.md），这样我在代码、issue、提交信息里用的词和项目一致。
54. 作为 agent，我希望有一份 ADR 说明为什么逻辑和渲染要分层，这样我不会在以后的改动里破坏这个约束，也不会重复争论这个问题。

### 美术 / 皮肤作者

55. 作为皮肤作者，我希望有一个明确的 Skin 接口（预加载资源、创建地图、为每种实体创建视图、提供主题 token），这样我知道做一套新皮肤需要实现什么。
56. 作为皮肤作者，我希望 EntityView 只需要处理"按快照同步"和"响应事件"两件事，这样写皮肤时不用碰游戏逻辑。
57. 作为皮肤作者，我希望 HUD 的颜色和字体从皮肤的主题 token 读取，这样换皮肤时 HUD 的风格也会跟着变。
58. 作为皮肤作者，我希望在 Storybook 里把同一个 story 切换到我的皮肤上，这样能直接和 Polygon 皮肤对比。

### 以后的后端开发者

59. 作为后端开发者，我希望关卡和单位配置通过一个异步的 LevelRepository 接口读取，这样我能换成从 server 拉取的实现。
60. 作为后端开发者，我希望玩家进度通过一个异步的 ProgressStore 接口读写，这样我能换成 server 存储。
61. 作为后端开发者，我希望所有服务都在一个组合根里组装，这样替换实现只需要改一个地方。
62. 作为后端开发者，我希望 server 可以复用同一份配置 schema 来校验数据，这样两边的数据格式不会不一致。

## Implementation Decisions

### 架构与分层

- **Simulation 和渲染分层**：Simulation 模块是纯 TypeScript，禁止依赖 Phaser、渲染层和数据服务，用 ESLint 的 import 限制规则强制。分层的目的是**可测试**和**让 agent 能从固定状态得到画面**，不是为了支持多种渲染器，也不是为了服务端运行。这一点要记录在 ADR-0001 里，同时写明代价：多一层同步代码；Phaser 的物理、计时器、tween 只能用在表现上。
- 依赖方向：场景 → 渲染 → Simulation；场景 → 数据服务 → 配置 schema；Simulation 只使用配置 schema 推导出的类型。
- 游戏逻辑始终在客户端运行。"server" 只指以后的数据存储。
- 单包结构，不拆 monorepo。工具链：pnpm、Vite、TypeScript strict、Vitest、ESLint、Prettier。依赖 `phaser@^4.2.1`、`zod`、Storybook 10（HTML + Vite 框架，加 vitest 和 docs 插件）、Playwright。

### Simulation

- 以固定 60Hz 步长运行，一个 tick 是 1/60 秒。配置中以"秒"为单位的值，进入 Simulation 时换算成以 tick 为单位。
- 世界坐标单位等于逻辑像素。格子大小 64，地图 15×10 格，对应逻辑分辨率 960×640。
- **SimState** 是可序列化的普通对象，包含：当前 tick、RNG 状态、金币、生命、波次进度（当前波的序号，以及出怪进度）、游戏结果（进行中 / 胜 / 负）、塔列表、敌人列表、子弹列表、下一个可用的 id。
  - 塔：id、kind、所在 Slot、剩余冷却、当前目标。
  - 敌人：id、kind、hp、maxHp、pathT（沿路径走过的距离）。坐标和朝向由 pathT 结合路径算出，不单独存。
  - 子弹：id、kind、发射它的塔、目标、当前坐标、目标最后已知的坐标。
- 实体用普通对象数组保存，逻辑写成按顺序执行的系统函数（出怪、移动、塔开火、子弹移动和命中、胜负判定），不引入 ECS。
- **SimEvent** 种类：开波、敌人生成、造塔成功、塔开火、子弹命中（带坐标，溅射时带半径）、敌人受伤、敌人被击杀（带奖励）、敌人漏过（带扣除的生命）、游戏结束（带结果）。
- **公开 API**：
  - 创建：输入关卡定义、单位目录、种子，以及可选的初始 SimState。
  - 只读的当前 `state`。
  - `advance(ticks)`：推进若干 tick，返回这段时间内产生的全部 SimEvent。
  - `placeTower(slotId, kind)`：成功时返回新塔的 id；失败时返回原因，可能是 Slot 已被占用、金币不足、Slot 不存在、游戏已结束。
  - `startNextWave()`：返回是否成功开波。
- **规则**：
  - 造塔只能在关卡定义的空 Slot 上，造的时候扣除造价。
  - 开波需要同时满足：游戏进行中、上一波已全部生成、场上没有敌人、还有下一波。
  - 每一波由若干出怪组组成，依次执行。每组规定敌人 kind、数量、出怪间隔。新敌人从 pathT = 0 出发。
  - 敌人每个 tick 前进自己的速度。走到路径终点就算漏怪：扣除漏怪伤害，敌人移除。
  - 塔在射程内选 pathT 最大的敌人作为目标。冷却结束而且有目标时，发射子弹。
  - 子弹追踪目标。目标先死了的话，子弹飞向目标最后已知的位置，到达后照样命中或爆炸。基础子弹只伤害目标；溅射子弹对命中点溅射半径内的所有敌人造成全额伤害。
  - 敌人 hp ≤ 0 时移除，玩家获得奖励金币。
  - 生命 ≤ 0 时立刻判负。最后一波已全部生成、场上没有敌人、生命 > 0 时判胜。游戏结束后，`advance` 不再改变状态。
- **占位数值**（不追求平衡）：

  | 塔 | 造价 | 射程 | 伤害 | 冷却 | 子弹速度 | 攻击方式 |
  |---|---|---|---|---|---|---|
  | basic | 50 | 160 | 10 | 0.5s | 480/s | 单体 |
  | splash | 80 | 128 | 8 | 1.2s | 320/s | 溅射，半径 48 |

  | 敌人 | HP | 速度 | 击杀奖励 | 漏怪伤害 |
  |---|---|---|---|---|
  | normal | 40 | 64/s | 5 | 1 |
  | fast | 20 | 128/s | 4 | 1 |

  初始金币 120，初始生命 10。第 1 波：normal ×8，间隔 0.8s。第 2 波：normal ×10，间隔 0.7s；然后 fast ×6，间隔 0.5s。第 3 波：normal ×14，间隔 0.6s；然后 fast ×10，间隔 0.4s。路径是从左侧进入、右侧离开的 S 形折线。Slot 约 12 个，都和路径相邻。

### 配置 schema

- 单位目录包含塔和敌人两部分，各自按 kind 索引，字段对应上面的两张数值表。塔需要有攻击方式字段（单体或溅射），溅射塔还要有溅射半径。
- 关卡定义包含：id、网格（列数、行数、格子大小）、路径（按顺序排列的格子坐标，取格子中心）、Slot 列表（id 和格子坐标）、初始金币、初始生命、波次列表（每波由若干出怪组组成）。
- TS 类型全部由 zod schema 推导。加载时要做引用校验：波次中的敌人 kind 必须在单位目录中存在。

### 数据服务

- `LevelRepository`：按 id 获取关卡定义；获取单位目录。两个方法都是异步的。本地实现读取打包进来的 JSON，读取时用 schema 校验，失败时抛出带字段路径的错误。
- `ProgressStore`：按关卡 id 读取和保存进度，都是异步的。进度包含：最好结果（胜 / 负）、最好结果时剩余的生命、更新时间。本地实现用 localStorage，并加 key 前缀。只有当新结果更好时才覆盖：胜比负好，结果相同时剩余生命多的更好。
- 组合根：接收一个环境描述（MVP 只有 local 一种），返回全部服务。不使用 DI 库。
- 只有场景层可以使用数据服务。Simulation 和渲染层不能接触。

### 渲染与皮肤

- **Skin** 接口包含：皮肤 id；主题 token（颜色和字体）；预加载资源（Polygon 皮肤里是空实现）；根据关卡定义创建 MapView；根据实体引用（实体类型、kind、id）创建 EntityView。
- **EntityView**：`sync`，根据实体快照和同步上下文（路径、关卡）更新显示；可选的 `onEvent`，响应 SimEvent 播放特效；`destroy`。
- **MapView**：画背景、路径、Slot；可以设置当前悬停的 Slot；`destroy`。
- **WorldRenderer**：每帧拿到 SimState 和事件后，按实体 id 和上一帧对比，新出现的创建视图，已存在的同步，消失的销毁；再把事件转发给相关视图。对应视图已被销毁的事件（比如击杀特效），交给皮肤在原地画一个短暂的特效。
- 皮肤在启动时选定，通过皮肤注册表按 id 查找。MVP 里只有 polygon 一个皮肤。游戏中不支持热切换。
- **Polygon 皮肤的外观**：

  | 对象 | 形状 | 颜色 |
  |---|---|---|
  | 背景 | — | `#1e2430` |
  | 路径 | 宽度为格子 60% 的折线带 | `#c9b28a` |
  | Slot | 格子描边；悬停时变亮，并预览射程 | `#3d5a4a` |
  | basic 塔 | 正方形 | `#3b82f6` |
  | splash 塔 | 六边形 | `#06b6d4` |
  | normal 敌人 | 菱形 | `#dc2626` |
  | fast 敌人 | 小三角形，朝向前进方向 | `#fb7185` |
  | 子弹 | 小圆点（8 边形） | `#facc15` |
  | 溅射爆炸 | 半透明圆环，约 0.2s 淡出 | `#facc15` |
  | 敌人血条 | 头顶细条，掉血部分为深灰 | `#22c55e` |
  | HUD 文字 / 金币 | — | `#f8fafc` / `#fbbf24` |
  | Debug overlay | 细线加等宽字体 | `#22d3ee` |

  塔开火时有一个短暂的放大或闪光，敌人受击时闪白。这两个效果用来证明事件通道是通的。
- **Debug overlay** 不属于任何皮肤，显示内容包括：塔的射程圈和指向当前目标的连线、敌人 id 和 hp/maxHp、路径折线和拐点编号、Slot id 和格子坐标、子弹 id。

### Phaser 场景

- **Boot 场景**：通过组合根创建服务；加载关卡和单位目录；按 URL 参数选择皮肤，默认是 polygon；调用皮肤的预加载；然后启动 Game 和 HUD 两个场景。
- **Game 场景**：创建 Simulation 和 WorldRenderer。用固定步长累加器按 60Hz 推进 Simulation，渲染每帧一次。处理 Slot 的悬停和点击；按 `D` 开关 Debug overlay。游戏结束时显示"胜利/失败 + 重来"浮层，并保存进度。
- **HUD 场景**：和 Game 场景并行运行，叠在上层，全部用 Phaser 绘制，颜色和字体只取自皮肤的主题 token。显示金币、生命、"第 n / N 波"；两个造塔按钮，显示名称和造价，选中的高亮，金币不足时变灰；"开始下一波"按钮，不能开波时变灰。数据来源是同一份 SimState 快照。
- 只支持桌面浏览器和鼠标。逻辑分辨率 960×640，用 FIT 方式等比缩放。不做主菜单。

### Fixture 与可视化

- **Fixture builder** 用链式调用描述局面：选关卡（同步读取打包的配置，不经过异步的 repository）、种子、金币、在指定 Slot 放指定的塔、在路径指定位置按指定间距放若干敌人。最后构建出关卡定义、单位目录和 SimState。
- **具名 Fixture** 至少包括：空地图、每种塔各一座、每种敌人各一个、基础塔正在开火、溅射塔命中一群敌人、敌人即将漏过、金币不足、最后一波、已胜利、已失败。
- **Storybook 挂载辅助函数**：把一个 Phaser 实例挂到 story 提供的 DOM 节点上，参数包括皮肤、是否开 Debug overlay、Fixture（或者单个实体的配置）、是否运行、速度、预先快进的 tick 数、是否显示 HUD。它返回一个 cleanup 函数，负责销毁 Phaser 实例，在 story 生命周期里注册。第一次渲染完成后设置一个全局"已就绪"标记，给截图工具用。
- **Story 目录**：
  - Entities：Towers（空闲、开火、悬停射程）、Enemies（满血、残血、受击）、Projectiles（基础子弹、溅射爆炸）。
  - Map：空地图、Slot 悬停。
  - HUD：正常、金币不足、不能开波、最后一波、胜利浮层、失败浮层。
  - Scenarios：每个具名 Fixture 一个。
  - Game：Playable，完整游戏，使用本地服务。
  - 所有 story 都有皮肤和 Debug 两个 Controls。Scenario 另外有运行、速度、快进 tick 数三个 Controls。story 可以在参数里声明截图时要用的 tick 数列表。
- **Shots 命令**：构建静态 Storybook，然后读取 story 索引。对每个 story 截取"无 Debug"和"有 Debug"两张图；声明了 tick 列表的 story，对每个 tick 再各截一组。等"已就绪"标记出现后截取 canvas。文件名由 story id、是否 Debug、tick 数组成，写入一个不进 git 的目录。支持按名称筛选。运行结束时打印生成的文件列表。

### 文档

- **CONTEXT.md 术语表**：Simulation、Tick、SimState（快照）、SimEvent、Path / pathT、Slot、Wave / Spawn group、Leak、Skin、EntityView、MapView、Theme token、Fixture、Scenario、Debug overlay、Shots。
- **ADR-0001**：逻辑和渲染分层的原因与代价（见"架构与分层"一节）。
- **agent 说明文件**：新增一节"开发命令"，列出 dev、test、storybook、shots（可带筛选）、lint。写明工作约定：改了渲染要跑 Shots 并查看截图；新增的视觉元素必须配 story 和 Fixture；需要交互调试时，用 Chrome MCP 打开 Storybook 或开发服务器。

## Testing Decisions

- **好的测试**只从公开接口观察外部行为：给定输入状态和操作，断言输出的 SimState 和 SimEvent，或者服务的返回值和抛出的错误。不测试内部系统函数的调用顺序、私有辅助函数，也不测试中间变量。重构 Simulation 内部时，测试不需要改。
- **Seam 1：Simulation 的公开 API**（主要的 seam）。用具名 Fixture 或 builder 构造初始状态，调用 `placeTower`、`startNextWave`、`advance`，然后断言 state 和事件。要覆盖：
  - 造塔成功扣钱，以及每一种失败原因；
  - 开波条件的每一项；
  - 出怪数量和间隔；
  - 移动和漏怪扣血；
  - 选择 pathT 最大的目标、射程边界；
  - 目标死后子弹仍飞到最后位置；
  - 溅射范围内外的伤害；
  - 击杀奖励；
  - 判负立即生效；判胜条件；结束后状态冻结；
  - 同一种子加同样操作，结果完全一致。

  路径计算、RNG、各系统函数**不单独测试**，通过这个 API 间接覆盖。
- **Seam 2：数据服务接口**。通过组合根拿到本地实现，用内存版 localStorage 代替真实的。要覆盖：合法配置能加载；非法字段被拒绝，错误里带路径；引用了不存在的 kind 被拒绝；进度只在结果更好时覆盖；没有记录时返回空。schema 不单独测试。
- **Seam 3：Story**（视觉层，不写像素断言）。每个 story 通过 Storybook 的 vitest 插件在浏览器里渲染一次，断言不抛异常、没有 console.error。Shots 生成的截图给人和 agent 查看，不做自动比对。渲染层、皮肤、固定步长累加器都不写单元测试。
- **Fixture 是共享的测试基础设施**：Seam 1 的测试和 Seam 3 的 Scenario story 用同一份具名 Fixture。
- **已有的测试先例**：仓库目前是空的，没有已有测试可以参照。第一批 Simulation 测试写好后，就是后续测试的范例。

## Out of Scope

- 游戏逻辑在服务端运行、联机、命令队列、回放。
- 任何 server 端实现。只做本地实现和接口。
- 移动端、触控、响应式布局。
- 主菜单、选关、多关卡、关卡编辑器。
- 塔升级、卖塔、技能、敌人特殊能力、塔的目标策略切换。
- 数值平衡、难度曲线。
- 贴图皮肤、音效、音乐。只提供接口和 Polygon 皮肤。
- 游戏进行中热切换皮肤。
- 用 DOM 或 React 做的 UI。
- 像素级视觉回归对比，以及渲染层的单元测试。
- 账号、排行榜、数据统计。
- 游戏内的 Gallery / Sandbox 场景。可视化只用 Storybook。

## Further Notes

- 截至 2026-10，npm 上 phaser 的 latest 版本是 4.2.1（正式版），Storybook 是 10.6.x。生态里没有专门的 Phaser + Storybook 集成包，所以挂载辅助函数需要自己写，代码量很小。
- WebGL context 数量有上限（浏览器一般约 16 个）。挂载辅助函数必须保证销毁，这是验收的一部分：连续切换 30 个 story 不出现 context 警告。
- 判断骨架是否真的方便扩充的标准是：新增一种攻击方式已有的塔，只需要改配置、皮肤、story 三处，不改 Simulation。
- 建议的实现顺序是：工程脚手架和文档 → 配置 schema 和数据服务 → Simulation（路径、出怪、漏怪、胜负）→ Simulation（塔、子弹、溅射、经济）→ 渲染核心和 Storybook → Debug overlay 和 Shots → Scenario story → 可玩游戏（Boot、Game、HUD 场景）→ story 冒烟测试和收尾。下一步可以用 to-tickets 把它拆成独立的 issue。
